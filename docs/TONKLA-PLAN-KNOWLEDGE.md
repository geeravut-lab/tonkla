## 3. สถาปัตยกรรมภาพรวม

```
 มือถือ/เดสก์ท็อป (PWA, Thai-first)
        │  HTTPS                                  ┌── LINE Platform (push Flex / webhook) ◄── พนักงานแตะการ์ด
        ▼                                         │
 Vercel (production only) ───────────────────────┤── Aivora hub (SSO ตั๋ว → /api/sso/exchange)
  Next.js 16: pages · Server Actions · Route Handlers
   ├─ client ของผู้ใช้ (ติด RLS) ───────────────►  Supabase Postgres (RLS ทุกตาราง)
   ├─ supabaseAdmin (service role)                  ├─ Auth (Google · Microsoft · custom session จาก Aivora)
   │   ใช้ได้เฉพาะ src/server/privileged/**          ├─ Storage (bucket ส่วนตัว, path = company/…)
   │   (SSO, cron, LINE webhook, fan-out, purge)     ├─ Realtime (ping ไม่มีข้อมูล, ตรวจสิทธิ์ที่ DB)
   └─ /api/cron/tick ◄── pg_cron + pg_net ───────────└─ pg_cron (tick ทุก 10 นาที)
```

หลักที่ถือ

1. **สิทธิ์ตัดสินที่ฐานข้อมูล (RLS)** — Server Action ใช้ client ของผู้ใช้เสมอ ไม่มีที่ไหนใช้ service role เพื่อ "ข้ามปัญหาสิทธิ์" · `supabaseAdmin` import ได้เฉพาะในโฟลเดอร์ `privileged/` (ตรวจด้วย lint)
2. **ซ่อนปุ่มไม่ใช่การปิดฟีเจอร์** — ทุก action เช็กสิทธิ์/สวิตช์ที่ server บรรทัดแรก
3. **ทุกการเขียนนับแถว** — `UPDATE` ที่ไม่ตรงแถวคือ "สำเร็จ" ในสายตา PostgREST จึงใช้ helper `mutate()` ที่ `.select('id')` แล้วตรวจจำนวนแถว (บั๊กเงียบ 2 ตัวของ RooSuk มาจากข้อนี้)
4. **ค่าที่ admin ตั้งได้ไม่ hard-code ซ้ำ** และ **fallback ต้อง "ทำงานต่อ"** (อ่านตั้งค่าไม่ได้ = ใช้ค่าในโค้ด)
5. **migration กับ deploy ไม่พร้อมกัน** — โค้ดต้องทนช่วงที่คอลัมน์ใหม่ยังไม่มี (ดัก `42703` / `PGRST204`)

## 4. การแยกข้อมูลรายบริษัท (สรุป — รายละเอียดใน DATA-MODEL)

- ทุกตารางที่มีข้อมูลธุรกิจมี `company_id` และ RLS ผ่านฟังก์ชัน `security definer` (`app.my_company_ids()`, `app.has_role(...)`) — ไม่เขียนเงื่อนไขซ้ำในแต่ละ policy
- **ผู้ใช้ที่ยังไม่ผ่านการอนุมัติ (`pending`) เห็นข้อมูลธุรกิจเป็นศูนย์** ไม่ว่าจะล็อกอินช่องทางไหน
- เห็นข้ามบริษัทได้เมื่อผู้ประสานงานของบริษัทอนุมัติ (`visibility='group'`) เท่านั้น
- ช่องไม่ระบุตัวตน (เฟส 2) แยกตารางที่ **ไม่มีคอลัมน์ผู้แจ้งและไม่มี company_id** และอ่านได้เฉพาะทีมกลาง
- Storage: path ขึ้นต้นด้วย `company_id/` และ policy ตรวจ prefix
- Realtime: topic ต่อคน/บริษัท ตรวจสิทธิ์ที่นโยบายบน `realtime.messages`
- มีเทส RLS แบบตาราง "ใครเห็น/แก้อะไร" (รายการเทสขั้นต่ำอยู่ใน DATA-MODEL §8) ทุก PR ที่แตะตารางหรือ policy ต้องเพิ่มเทส

### 5.2 ค่าคงที่ของ SSO สำหรับ Tonkla

| ค่า | ใน SSO doc (e-voa) | ของ Tonkla |
| --- | --- | --- |
| `APP_SLUG` | `e-voa` | `tonkla` — **ต้องให้เจ้าของ hub ลงทะเบียน slug นี้ [D12]** |
| `CALLBACK` | `https://e-voa.vercel.app/sso/callback` | `https://tonkla-th.vercel.app/sso/callback` |
| `HUB_URL` ของ SSO doc | `https://e-voa.vercel.app` | ไม่ใช่ hub จริง — ปุ่มล็อกอินและการแลกตั๋วใช้ `https://aivora-lc.netlify.app` ตามขั้นที่ 2 และ 8 (ยืนยันกับเจ้าของอีกครั้ง) |
| `SUPABASE_URL` | โปรเจกต์ e-voa | `https://yfowqsfyfvzgwqdbkykx.supabase.co` |
| `SUPABASE_SERVICE_ROLE` | ใน env | เก็บที่ Vercel env เท่านั้น ห้ามเข้า repo/log/`NEXT_PUBLIC_*` |

ข้อต่างจาก SSO doc ที่ Tonkla ต้องทำ (เพราะ role ไม่ใช่เรื่องให้ผู้ใช้เลือกเอง)

- ผู้ใช้ใหม่จาก SSO → `profiles.status='pending'` และพาไปหน้า "ขอเข้าร่วมบริษัท / ใส่รหัสเชิญ" ซึ่งเป็นหน้าปกติของแอป (ไม่ใช่ส่วนของ `/sso/callback`) — **ไม่มีหน้าให้เลือกบริษัทหรือบทบาทเองโดยไม่ผ่านการอนุมัติ**
- `role_assignments` เขียนได้ผ่านฟังก์ชัน SQL ที่ตรวจสิทธิ์เท่านั้น และมีเทส "ยิง update ด้วย anon key เปลี่ยน role/สถานะตัวเอง ต้องถูกปฏิเสธ" (ทั้งก่อนและหลังตั้งค่า)
- เส้นทาง bootstrap หลัง `setSession` มีที่เดียว เรียกตรง ๆ จากทั้ง SSO และ login ปกติ (ห้ามเขียนสองชุด) และมี timeout 15 วินาที + checkpoint `console.info` 6 จุด

### 5.3 การรับพนักงานเข้า (provisioning) **[D4]**

1. ผู้ประสานงานบริษัท/ทีมกลาง นำเข้ารายชื่อ (CSV) → `roster_entries` (อีเมลที่ทำงาน, รหัสพนักงาน, แผนก, ตำแหน่ง)
2. ผู้ใช้ล็อกอินครั้งแรก: ถ้า **อีเมลที่ยืนยันแล้ว** (Google/Microsoft) ตรงรายชื่อ → เปิดใช้งานทันที
3. ถ้าไม่ตรง หรือมาทาง LINE ที่ไม่มีอีเมล → ใส่ **รหัสเชิญ** จากผู้ประสานงาน หรือส่ง **คำขอเข้าร่วม** ให้ผู้ประสานงานอนุมัติ
4. พนักงานออก → `memberships.status='ended'` สิทธิ์หายทันที (RLS ตรวจสมาชิกที่ active) ข้อมูลที่ส่งไว้คงอยู่แต่ไม่ผูกกับตัวบุคคล (ดู PDPA ใน DATA-MODEL §9)

## 6. การ deploy และสภาพแวดล้อม

- **Production เท่านั้น** (R1): ตั้งใน Vercel ให้ build เฉพาะ branch `main` (Ignored Build Step ตรวจ `VERCEL_GIT_COMMIT_REF` + `vercel.json` ปิด deployment ของ branch อื่น — ตรวจรูปแบบที่ถูกต้องกับเอกสาร Vercel ตอนทำ) · PR ตรวจด้วย GitHub Actions ไม่มี URL พรีวิว
- **Supabase โปรเจกต์เดียว = production** ความเสี่ยง: migration ผิดกระทบข้อมูลจริง จึงบังคับ
  - ทุก schema change เป็นไฟล์ migration ใน `supabase/migrations/` เท่านั้น (ห้ามแก้ผ่านหน้าเว็บ Supabase) และผ่านเทส PGlite + `supabase db lint` ใน CI ก่อน
  - migration แบบทำลาย (drop/rename) ทำเป็น 2 ขั้น (expand → contract) และขออนุมัติก่อนรัน
  - บริษัททดลองตั้ง `is_demo=true` ให้แยกข้อมูลทดสอบออกจากข้อมูลจริงและลบทิ้งได้
  - ตรวจ backup/PITR ของแพ็กเกจ Supabase ก่อนเปิดนำร่อง
- ตัวแปรสภาพแวดล้อม (ค่าอยู่ที่ Vercel เท่านั้น ในไฟล์เก็บแต่ชื่อ): `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `CRON_SECRET`, `AIVORA_HUB_URL`, `AIVORA_APP_SLUG`, `LINE_CHANNEL_SECRET`, `LINE_CHANNEL_ACCESS_TOKEN`, `LINE_BASIC_ID`, `MS_ENTRA_*` (ฝั่ง Supabase), คีย์อีเมลและคีย์ AI (เมื่อถึงเวลา) — **ไม่มี `NEXT_PUBLIC_` นำหน้าความลับ**
- ความปลอดภัย: CSP + security headers, `grep service_role|SUPABASE_SERVICE build/` ต้องไม่เจออะไร (ขั้นทดสอบของ SSO doc), secret scanning ใน GitHub, ห้ามข้อมูลพนักงานจริงใน repo/seed
- Auth redirect ของ Supabase: เฉพาะ `https://tonkla-th.vercel.app/**` (ไม่มี wildcard ของ preview เพราะไม่มี preview)

## 12. กติกาการทำงานที่เจ้าของสั่ง (บันทึกแล้วใน `CLAUDE.md`)

1. ตอบเจ้าของเป็นภาษาไทย
2. **ปิดท้ายทุกงานที่สำเร็จด้วยหัวข้อ "ขั้นตอนถัดไป"**: สิ่งที่เหลือใน milestone/เฟสนั้น และสิ่งที่จะทำได้ในเฟสถัดไป พร้อมข้อเสนอแนะ ให้เจ้าของเลือกสั่ง
3. Deploy: production เท่านั้น ไม่ทำ preview
4. ทุกปุ่ม/เมนูที่รอ ต้องมีตัวหมุนโหลด (§7.1)
5. ทำบน branch + PR · ไม่ commit ตรง `main` · ไม่มีความลับ/ข้อมูลพนักงานจริงใน repo
6. สร้างเฉพาะเฟสปัจจุบัน — ยกเว้นรายการที่เจ้าของสั่งชัดเจน (R5, R11, R12 ถูกบันทึกเป็นข้อยกเว้นแล้วใน spec)
7. ก่อนรัน migration ที่ทำลายข้อมูลหรือเปลี่ยนค่า production ที่ย้อนไม่ได้ ถามก่อน
